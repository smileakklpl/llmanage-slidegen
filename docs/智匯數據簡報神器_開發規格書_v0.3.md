## 1. 專案目標(一句話)

使用者以一段自然語言指令 + 一份多工作表 Excel 報表,系統在遠低於 15 分鐘內,產出:

1. 一份套用台新新光金控模板、顧問風格、**每張圖表皆為 PPT 原生可編輯物件、數字 100% 正確且可追溯**的簡報(.pptx)
2. 一份與簡報圖表一一對應的原始資料 Excel(.xlsx)
3. 自動寄送至指定收件人(模擬信箱)

並具備:**模型可抽換**(雲端 ↔ 地端 LLM)與**資料更新可重生成**(Refresh)兩項架構特性。

## 2. 範圍界定

### 2.1 In Scope(必做)

- F1 數據智能解析引擎
- F2 PPT 模板綁定與原生圖表生成
- F3 Excel 繪圖資料同步輸出
- F4 自動寄送機制
- F5 一次性 prompt 端到端流程(Web UI 或 API 觸發)
- A1 模型抽換層(LLM abstraction)
- A2 Spec 驅動之重生成機制(資料更新 → 一鍵 Refresh)

### 2.2 Stretch(加分/行有餘力)

- S1 口述驅動模式(語音轉文字 → Agent 彙整跨表 → 產出)(+5%)
- S2 使用 Kiro 作為 AI 整合開發環境(+5%)
- S3 多輪對話調整(「把 P.7 改成 Top 5」)
- S4 排程自動同步(每月自動抓新資料 → 生成 → 寄送,Demo 以示意呈現)
- S5 **模型分層呼叫(v0.3 新增,行有餘力)**:依頁面權重分層用模型——intent 與重點頁(Exec Summary、對台新策略建議)用高階模型,其餘敘事用中階,信件摘要用輕量模型;fallback 鏈:高階 throttle 時降級至中階(品質換可用性),與 `global.`/`us.` 前綴路由並列兩層 fallback。**前置條件:FR-A1 之 per-stage 模型路由設定(必做)**;分層「策略」本身為加分項,預設全案單一模型即可跑通。

### 2.3 Out of Scope(明確不做)

- PPT 圖表以「外部連結 Excel」方式即時連動(路徑脆弱、與寄送情境衝突)
- 閉源 SaaS 簡報生成服務
- 真實 SMTP 對外寄信(以 MailHog 模擬信箱為準,見 FR-4.1)

## 3. 需求規格

### 3.1 功能需求(FR)

#### FR-1 數據智能解析引擎
- FR-1.1 支援多工作表 .xlsx 輸入(範例:金管會信用卡業務統計 114 年 1-12 月)。
- FR-1.2 自動辨識工作表結構:表頭列、機構名稱欄、月份欄(格式如 `11401`–`11412`)、單位。
- FR-1.3 自動建立跨表關聯(以機構名稱為 key 對齊各指標工作表)。
- FR-1.4 支援之衍生計算(全部由確定性程式碼完成,禁止 LLM 計算):
  - 市占率(個別 / 總計)
  - 月增率(MoM)
  - 有效卡率(有效卡數 / 流通卡數)
  - 平均每卡簽帳金額(當月簽帳金額 / 有效卡數)
  - 排名(Top N)
  - 加總、平均
  - **趨勢外推(v0.2 新增)**:線性回歸 / 移動平均之短期外推,由 engine 確定性計算(scikit-learn 內嵌於管線)。MetricStore 標記 `"type": "forecast"`,renderer 對 forecast 類數值**強制**加「推估值」註記於版面。提案敘事框架:「預測模組以 sklearn 內嵌(輕量、零延遲),介面已抽象,資料量放大後可無縫遷移 SageMaker」——不為名詞而部署 SageMaker endpoint。
- FR-1.5 **防呆規則(關鍵)**:資料範圍外之指標不得產出。
  - 例:僅有 114 年資料時,**不得**計算/呈現 YoY(附件三 P.3 被點名之錯誤)。
  - **外推防呆(v0.2 新增)**:資料點不足(< 6 個月)時 forecast 類指標標記 `computable: false`,理由「樣本不足以外推」。
  - 引擎需輸出「可計算指標清單」,敘事層只能引用清單內指標。
- FR-1.6 所有計算結果附帶**來源追溯資訊**(來源工作表、儲存格範圍、計算公式)。

#### FR-2 PPT 模板綁定與原生圖表生成
- FR-2.1 以附件一模板為母版:封面、目錄、章節頁、內容頁、結尾頁版型與品牌元素(「智慧好夥伴」頁腳、頁碼)一致。
- FR-2.2 圖表一律為 **PPT 原生 chart**(內嵌 chart XML + embedded workbook),驗收標準:於 PowerPoint 右鍵 →「編輯資料」可開啟資料表,可縮放、改色、改數字。
- FR-2.3 支援圖型:長條圖(含堆疊)、橫條圖、折線圖(含雙軸)、圓餅圖、散點圖。
  - 熱力圖:以原生表格 + 儲存格底色(資料驅動之色階)模擬。
- FR-2.4 表格一律為 **PPT 原生 table 物件**,禁止文字方塊拼貼。
- FR-2.5 頁面上出現的每一個數字,必須來自 FR-1 計算結果(單一真相來源),禁止 LLM 生成之數字直接落版。
- FR-2.6 預設輸出 16 頁「銀行信用卡市場分析與經營洞察簡報」,章節依附件二:Executive Summary / 市場整體概況 / 同業成長及競爭分析 / 客戶活躍度 / 獲利能力 / 風險與警訊 / 未來趨勢推測 / 對台新的策略建議。頁數與章節可由使用者 prompt 覆寫。「未來趨勢推測」章節之數字一律引用 FR-1.4 之 forecast 類指標(帶「推估值」註記),writer 不得自行推測數值。

#### FR-3 Excel 同步輸出
- FR-3.1 每張簡報圖表對應一個工作表,命名規則:`P.{頁碼}_{指標名稱}`(對齊附件四)。
- FR-3.2 各工作表包含:圖表之原始資料 + 以該資料建立之 Excel 原生圖表物件。
- FR-3.3 Excel 數值與 PPT 內嵌數值必須完全一致(自動化比對測試,見 §7)。
- FR-3.4 **數字溯源附錄(v0.2 新增)**:Validator 之三方比對結果轉製為「數字溯源附錄」——每個簡報數字 → 來源工作表/儲存格 → 計算公式 → 驗證狀態。以簡報附錄頁(不計入使用者指定頁數)或獨立 PDF 隨信附上。附錄本身亦須通過 T1 比對。定位:金融業可稽核性之 Demo 亮點。

#### FR-4 自動寄送
- FR-4.1 生成完成後,將 .pptx 與 .xlsx 以附件寄送至指定收件人。**首選:MailHog(與 API 同一 Docker Compose stack)**;Mailer 一律 **SMTP + S3 雙寫**(雙寫非部署考量,係支撐可追溯敘事與 Refresh 寄送紀錄,不得省略);備案:自建極簡收件匣(讀 S3 顯示)。
- FR-4.2 信件內文由 LLM 生成摘要(3–5 句重點),收件人、主旨可由 prompt 指定。
- FR-4.3 Demo 需能展示收件匣畫面。

#### FR-5 一次性 Prompt 流程
- FR-5.1 輸入:自然語言指令(參考附件二)+ Excel 檔上傳。
- FR-5.2 意圖解析(LLM):抽取 → 頁數、簡報對象、分析指標、章節結構、圖表偏好、收件人。輸出為結構化 JSON(schema 驗證 + 失敗重試)。
- FR-5.3 **非同步 job 模式(v0.3 改)**:端到端耗時分鐘級,同步 HTTP 必撞逾時,一律非同步——
  - `POST /generate` → 立即回 `202` + `job_id`
  - `GET /jobs/{job_id}` → 輪詢(前端間隔 2–3 秒),回傳 job 狀態
  - job 狀態落 S3(非記憶體),schema:`{stage, progress, per_stage_timing, error, artifacts}`;`per_stage_timing` 同時作為 T4 速度測試之數據來源
  - `POST /replay` 同樣走 job 模式
  - 全流程無需人工介入即完成 F1–F4;介面顯示各階段進度。

#### FR-A1 模型抽換層
- A1.1 所有 LLM 呼叫經統一介面(OpenAI 相容格式;實作採 LiteLLM 或自建 thin wrapper)。
- A1.2 以設定檔切換後端:AWS Bedrock(競賽預設)/ 地端 vLLM/Ollama(企業落地情境)。程式碼零改動。
- A1.5 **(v0.3 新增)per-stage 模型路由**:intent / writer(可細至頁級)/ mailer 各自可由環境變數指定模型(`LLM_MODEL_INTENT`、`LLM_MODEL_WRITER`、`LLM_MODEL_WRITER_KEYPAGES`、`LLM_MODEL_MAILER`)。此為必做之「能力」;分層「策略」見 S5。
- A1.3 LLM 職責僅限:意圖解析、洞察敘事、信件摘要。三者皆為結構化輸出。
- A1.4 驗收:Demo 可現場切換至開源模型並完整跑通(文案品質可異,數字不可異)。

#### FR-A2 Spec 驅動重生成(Refresh)
- A2.1 每次生成保存一份 **DeckSpec**(JSON):記錄每頁之版型、指標、資料查詢、計算邏輯、圖型、敘事重點。
- A2.2 當來源資料更新(重新上傳 / S3 物件變更),依同一 DeckSpec 重跑管線,產出數字更新、版型不變之新版 PPT + Excel。S3 事件通知以 prefix `uploads/` 過濾,避免 outputs/ 寫回觸發無限迴圈。
- A2.3 Demo 橋段:上傳「勘誤版 Excel」→ 一鍵 Refresh → 對照新舊 PPT 數字已同步、版型完全一致。

### 3.2 非功能需求(NFR)

| 編號 | 需求 | 目標 |
|---|---|---|
| NFR-1 | 端到端速度 | ≤ 5 分鐘(內部目標;競賽上限 15 分鐘)。各頁敘事 LLM 呼叫平行化,**預設平行度 16(全頁一次打完),防禦下限 4**;exponential backoff 保留為防禦性設計。平行度與模型皆參數化為環境變數(`LLM_MAX_PARALLEL`、`LLM_BACKOFF_BASE`、`LLM_MODEL_*`),現場調參不動程式碼(調參流程見執行手冊)。**敘事快取**:同一 DeckSpec + 同一資料指紋不重打 LLM。 |
| NFR-2 | 數字正確率 | 100%。以自動化比對(來源 Excel ↔ 計算層 ↔ PPT 內嵌資料 ↔ 輸出 Excel)驗證。 |
| NFR-3 | 開源優先 | 管線核心(pandas、openpyxl、python-pptx、FastAPI、LiteLLM)全開源;LLM 走託管/地端皆可之抽象層。 |
| NFR-4 | 可部署性 | Docker Compose 單機部署(目標環境 EC2,環境細節見執行手冊);容器映像預先 build 推至公開 registry(GHCR),部署端僅 pull;所有 SDK client **顯式指定 region**(值由環境變數 `AWS_REGION` 注入,禁止依賴環境預設);提供 Live Demo URL。 |
| NFR-5 | 可追溯性 | 任一簡報數字可回溯至來源儲存格與計算公式(存於 DeckSpec / 附錄)。 |
| NFR-6 | 通用性 | 解析引擎不 hardcode 信用卡資料欄名;以「結構偵測 + 指標定義檔」支援其他報表(至少口頭論述 + 一個小型第二資料集驗證)。 |

## 4. 系統架構

### 4.1 管線(Pipeline)

```
使用者 Prompt + Excel 上傳
        │
        ▼
[1] Intent Parser(LLM,JSON 輸出)
        │  → 頁數 / 指標 / 章節 / 圖型偏好 / 收件人
        ▼
[2] Data Engine(pandas,確定性)
        │  → 結構偵測 → 跨表對齊 → 指標計算 → 防呆過濾
        │  → 產出 MetricStore(含來源追溯)
        ▼
[3] Insight Writer(LLM,平行,JSON 輸出)
        │  → 每頁標題、洞察敘事、重點句(只能引用 MetricStore 之值)
        ▼
[4] Renderer(python-pptx / openpyxl,確定性)
        │  → 套模板 → 原生 chart/table → 同步 Excel
        ▼
[5] Validator(確定性)
        │  → PPT 內嵌資料 ↔ MetricStore ↔ 輸出 Excel 三方比對
        ▼
[6] Mailer(模擬信箱)
        │
        ▼
   DeckSpec 落地保存(供 Refresh 重放)
```

### 4.2 部署對應(v0.3 修訂:僅邏輯視圖,環境實況與選型理由見執行手冊)

- **容器主機**:EC2 + Docker Compose(單機多容器:frontend+api、MailHog)
- **前端**:API 容器直接 serve 靜態頁,並提供 job 輪詢端點
- **LLM**:Bedrock(經 llm adapter 抽象;可換地端 vLLM;per-stage 路由見 FR-A1.5)
- **檔案儲存**:S3(uploads / outputs / deckspecs / jobs / mail;**所有輸入輸出一律落 S3**,含語音檔與 job 狀態——統一「可追溯」敘事)
- **Refresh 迴路(閉合)**:S3 Event(prefix 過濾,見 A2.2)→ Lambda → 回呼 API 之 `POST /replay`(帶 DeckSpec 路徑)→ 管線重跑 → 新產出寫回 S3 → 寄送。Lambda 於競賽帳號之可用性待驗(見執行手冊),UI 按鈕為確定可用之並行觸發(**雙觸發設計**)。
- **口述(Stretch)**:音檔上傳 → S3 → Amazon Transcribe(非同步)→ 文字進 Intent Parser。

### 4.3 模組切分與介面(供分工)

| 模組 | 負責功能 | 輸入 | 輸出 |
|---|---|---|---|
| `intent` | FR-5.2 | prompt 文字 | `IntentSpec`(JSON) |
| `engine` | FR-1 | xlsx + IntentSpec | `MetricStore`(JSON/parquet) |
| `writer` | FR-2.6 敘事 | MetricStore + IntentSpec | `PageNarrative[]`(JSON) |
| `renderer` | FR-2 / FR-3 | MetricStore + Narrative + 模板 | .pptx + .xlsx |
| `validator` | NFR-2 | .pptx + .xlsx + MetricStore | 驗證報告(pass/fail) |
| `mailer` | FR-4 | 檔案 + 收件人 | 寄送紀錄 |
| `deckspec` | FR-A2 | 上述全部 | DeckSpec JSON;`replay(deckspec, new_data)` |
| `llm` | FR-A1 | — | 統一 `complete_json(prompt, schema)` 介面 |

模組間僅以上述 JSON 契約溝通,任何人不得跨模組直接取值。

## 6. LLM 使用原則(全隊共識)

1. **LLM 永遠不計算、不產生數字。** 所有數值來自 `engine`;`writer` 的輸出若含數字,必以 `{{metric_key}}` 佔位符引用,由 renderer 代入實際值。
2. LLM 輸出一律 JSON + schema 驗證,失敗自動重試(上限 2 次),再失敗則落入預設模板文案。**(v0.3 明定)`complete_json()` 為 llm adapter 之統一入口,內建職責順序:markdown fence 剝除 → JSON parse → schema 驗證 → 重試**。fence 剝除是 adapter 的份內事(部分模型穩定輸出 ```json 圍欄),writer 與任何呼叫端不得自行處理模型輸出怪癖。
3. Prompt 模板集中管理於 `prompts/` 目錄,注明適配之最低模型能力,供地端弱模型調校。

## 7. 驗證與測試

- T1 **三方數值比對**(自動化,CI 必跑):輸出 Excel ↔ PPT 內嵌 workbook ↔ MetricStore 全數一致。
- T2 **防呆測試**:餵入僅 114 年資料,斷言輸出全文與圖表不含 "YoY"/年增率。
- T3 **原生性測試**:程式檢查 .pptx 內 chart part 存在 embedded workbook;人工抽查右鍵「編輯資料」。
- T4 **速度測試**:標準資料集端到端 ≤ 5 分鐘,記錄各階段耗時。
- T5 **模型抽換測試**:Bedrock 與開源模型各跑一次,T1–T3 皆須通過。
- T6 **Refresh 測試**:修改來源某數值 → replay → 僅該數值相關頁面數字變動,版型 diff 為零。
- T7 **附件三錯誤對照測試(v0.2 新增)**:官方點名之 8 項已知錯誤逐項斷言不再現——
  | # | 頁 | 錯誤 | 斷言 |
  |---|---|---|---|
