## 1. 需求澄清

命題原文要求：

> 簡報中的圖表，**右鍵點擊「編輯資料」**，即可查看/修改原始資料表。

這**不是**「PPT 圖表連結到外部 Excel 檔案」，而是 PowerPoint 原生機制：圖表右鍵「編輯資料」開啟的，是**內嵌在 `.pptx` 檔案內部**的一份工作簿（embedded workbook），跟外部獨立的 `.xlsx` 檔案是兩個不同的東西。

因此正確的設計方向是：**生成 PPT 時，讓圖表的內嵌工作表與畫面顯示值同源自同一批解析後資料**，而非事後去「連結」一份外部 Excel。

---

## 2. 技術原理

### 2.1 PPT 圖表背後的三個部件

一張 PowerPoint 原生圖表，實際由三個部分組成：

| 部件 | 位置 | 作用 |
|------|------|------|
| Chart XML 快取值（`c:numCache` / `c:strCache`） | `.pptx` 內 `ppt/charts/chart1.xml` | PowerPoint **顯示**圖表時直接讀這裡，不會每次開檔都重新讀工作簿 |
| 內嵌工作簿（embedded workbook） | `.pptx` 內 `ppt/embeddings/Microsoft_Excel_Worksheet#.xlsx` | 使用者右鍵「編輯資料」時開啟、修改的來源 |
| 圖表物件本身（graphic frame） | slide XML 內 | 決定圖表在投影片上的位置、大小、類型 |

**風險點**：若這三者（尤其前兩者）數字不一致，就會出現「畫面上顯示 A 值，但右鍵編輯資料打開卻是 B 值」的問題——這正是附件三錯誤範例（P.5、P.7 座標軸與數值有誤）的技術根源之一。

### 2.2 解決方案：單一資料入口

python-pptx 的 `shapes.add_chart()` API，在**生成階段**會自動把同一批輸入資料，同時寫入 chart XML 快取與內嵌工作簿。只要全系統統一走這一個入口，兩者就保證一致，不需要額外的「同步」或「連結」邏輯。

```
ChartSpec（結構化資料）
        │
        ▼
   add_chart()  ←── 唯一入口，不手動操作底層 XML
        │
        ├──→ chart XML cache（畫面顯示值）
        └──→ 內嵌 workbook（右鍵「編輯資料」看到的值）

上述兩者由同一次 API 呼叫產生，天生一致。
```

**這個原則不因導入多 Agent 架構而改變**——無論是哪個 Agent 決定「要畫哪張圖」，最終落地生成圖表時，一律只能透過這個單一入口，Agent 本身沒有機會繞過去手動塞數字。

## 3. 整體資料流（v0.2：兩階段資料管線 + 多 Agent 協作）

v0.1 版本把「解析引擎」畫成一個黑箱步驟。v0.2 把這個步驟拆成兩個明確階段，並在敘事/圖表決策層引入多 Agent 協作：

```
┌──────────────────────────────────────────────────┐
│  Stage 0：原始數據檔案                              │
│  Excel 原始報表（金管會月報／附件四，多工作表寬表）    │
└────────────────────┬───────────────────────────┘
                     ▼
┌──────────────────────────────────────────────────┐
│  Stage 1：解析引擎 (engine)                         │
│  - pandas / openpyxl，確定性計算                     │
│  - 跨表關聯、欄位對應、加總計算                        │
│  - YoY / MoM、市占率、有效卡率、排名等指標計算          │
│  - 防呆：資料範圍外的指標不計算（如缺基期不算 YoY）     │
└────────────────────┬───────────────────────────┘
                     ▼
┌──────────────────────────────────────────────────┐
│  Stage 2：分析後 Excel（新產出物，本次新增）          │
│  = 「分析結果」以 .xlsx 形式落地保存                  │
│  - 每個工作表對應一組已計算好的指標時間序列/分類數據    │
│  - 命名規則：P.{頁碼}_{指標名稱}（對齊附件四慣例）      │
│  - 這份檔案同時是：                                  │
│    (a) MetricStore 的持久化形式（可重複讀取、可稽核）   │

└────────────────────┬───────────────────────────┘
                     ▼
┌──────────────────────────────────────────────────┐
│  Stage 3：MetricStore 載入                          │
│  將「分析後 Excel」讀入記憶體，建立唯一真相來源         │
│  (metric_store.py)                                 │
│  - 對外提供 catalog_for_llm()：只給 LLM 看 metadata   │
│    （metric_key / 名稱 / 單位 / 類別預覽），不給實際數值 │
│  - 對內提供 get(metric_key)：查表取得實際數值           │
└────────────────────┬───────────────────────────┘
                     ▼
┌──────────────────────────────────────────────────┐
│  Stage 4：多 Agent 協作（詳見第 4 節）                │
│                                                     │
│  ① 章節規劃 Agent → SectionPlan[]                    │
│  ② 圖表 Agent（含圖表 skill）→ ChartPlan[] → ChartSpec │
│  ③ 文字生成 Agent → PageNarrative（含 metric 佔位符）  │
│  ④ 審查 Agent → APPROVED / REJECTED(重試指定 Agent)   │
└────────────────────┬───────────────────────────┘
                     ▼
┌──────────────────────────────────────────────────┐
│  Stage 5：Renderer                                  │
│  chart_builder.py：CHART_SKILLS[chart_type](...)     │
│  → add_chart() 單一入口                              │
└────────────────────┬───────────────────────────┘
        ┌────────────┴────────────┐
        ▼                         ▼
  chart XML cache           內嵌 workbook
 （畫面顯示值）             （右鍵編輯資料值）
        │                         │
        └────────────┬────────────┘
                     ▼
          兩者透過同一入口生成，保證一致
                     │
                     ▼
        （另一條獨立路徑）FR-3 外部稽核用 .xlsx
        由「分析後 Excel」（Stage 2）延伸產出，
        確保與 PPT 內嵌工作表數字同源
```

### 3.1 為什麼要新增「分析後 Excel」這個中間產出物

1. **可稽核**：使用者或審查者可以直接打開這份 Excel，核對解析引擎算出的每一個指標，不需要打開 PPT 或翻程式碼。
2. **可重放（Refresh）**：對應規格書 A2「Spec 驅動之重生成機制」，原始數據更新後，只需重跑 Stage 1（解析引擎）產生新的「分析後 Excel」，Stage 4 之後的流程可原封不動重放。
3. **與 FR-3 的自然銜接**：FR-3 要求輸出「與圖表對應之原始資料 Excel」，這份「分析後 Excel」本身就是最直接的候選來源，不需要另外重新彙整一次。
4. **切斷 LLM 與原始檔案的距離**：多 Agent 系統只讀「分析後 Excel」（透過 MetricStore），完全不觸碰命題方提供的原始 `source/附件四...xlsx`，降低誤讀多工作表複雜格式的風險。

**重要原則不變**：LLM（無論是哪個 Agent）只負責決策（畫哪種圖、寫什麼洞察、審查邏輯是否合理），**不參與任何數值計算**。所有數字必須來自 Stage 1 解析引擎 → Stage 2 分析後 Excel → Stage 3 MetricStore 這條確定性鏈路，避免 LLM 幻覺造成數字與 Excel 不符（對應附件三揭露的問題）。

## 4. 多 Agent 協作架構

### 4.1 設計理念

原先命題要求可以用單一 LLM 呼叫（prompt → 直接出圖表數據）處理，但這樣會導致 LLM 同時決策「畫什麼」與「數字是多少」，違反「LLM 不計算數字」的核心原則。因此拆成四個職責單一的 Agent，圖表決策與數值計算之間永遠隔著一層**查表動作**（MetricStore），LLM 沒有機會編造不存在的數字。

Orchestrator（確定性程式碼，非 LLM）負責在四個 Agent 間傳遞資料契約、觸發防呆檢查、控制中斷點（例如等待使用者確認章節），不交給 LLM 自行判斷流程走向。

### 4.2 四個 Agent 的資料契約

```
使用者描述 + (可選)章節清單
        │
        ▼
① 章節規劃 Agent (SectionPlannerAgent)
   input:  user_prompt, existing_sections?
   output: { status: "NEEDS_CONFIRMATION" | "READY",
             sections: SectionPlan[],
             question_to_user?: string }
   規則：若使用者未提供章節清單，必須回傳 NEEDS_CONFIRMATION，
         由 Orchestrator 中斷流程等待使用者輸入，不可自行假設。
        │ (使用者確認後，狀態變為 READY)
        ▼
② 圖表 Agent (ChartAgent) —— 本身是一個小型 Orchestrator，內部依序執行：
   a. LLM 呼叫：input  = SectionPlan + MetricStore.catalog_for_llm()（不含數值）
              output = ChartPlan[]（每項僅含 metric_key 引用，無數字欄位）
   b. 確定性檢查：chart_planner.validate_chart_plan()
      - metric_key 是否存在於 MetricStore
      - chart_type 是否為已註冊 skill
      - series_names 是否存在於該 metric 下
   c. 確定性查表：chart_planner.resolve_chart_plan() → ChartSpec / ScatterSpec
   d. 依 chart_type 從 CHART_SKILLS registry 取出對應函式，實際呼叫產生圖表
        │
        ▼
③ 文字生成 Agent (NarrativeWriterAgent)
   input:  SectionPlan + 已 resolve 的 ChartSpec（可讀取實際數值，僅供「引用」）
   output: PageNarrative { text_with_placeholders, cited_metric_keys }
   限制：輸出文字中的數字只能以 {{metric_key}} 佔位符表示，
         禁止輸出字面數值；renderer 於最終組裝時才代入實際值。
        │
        ▼
④ 審查 Agent (ReviewerAgent) —— 分兩層檢查：
   數值層（確定性規則，不需 LLM）：
     - cited_metric_keys 是否都在 MetricStore 可計算指標清單內
     - text_with_placeholders 是否含「裸數字」（正規表達式偵測）
   敘事/邏輯層（LLM 語意審查）：
     - 圖表類型是否適合資料形狀（比例資料誤用折線圖等）
     - 敘事方向是否與數值正負號矛盾
       （對應附件三 P.7「10.7% 高於 11.0%」的邏輯錯誤類型）
   output: APPROVED | REJECTED(reason, target_agent)
           REJECTED 時，Orchestrator 將任務退回 target_agent 重跑
```

### 4.3 圖表 Skill 註冊機制

圖表 Agent 不需要知道每種圖表的實作細節，只需要知道 skill 名稱字串。`chart_builder.py` 維護一個 registry：

```python
CHART_SKILLS = {
    "column": add_category_chart,   # 長條圖／排名圖／成長率圖
    "bar": add_category_chart,      # 橫條圖
    "pie": add_pie_chart,           # 市占率圖
    "scatter": add_scatter_chart,   # 規模 vs 成長散點圖
    # "heatmap": 走原生表格 + 儲存格底色模擬，不透過 add_chart()，
    #            另外註冊在 table_builder.py（尚未實作）
}
```

新增圖表類型時，只需在此註冊一個函式，圖表 Agent 與 Orchestrator 端無需改動。

### 4.4 ChartPlan：LLM 唯一允許輸出的圖表決策格式

```python
@dataclass
class ChartPlan:
    slide_title: str
    chart_type: Literal["column", "bar", "pie", "line", "scatter"]
    chart_title: str
    metric_key: str          # 引用 MetricStore，不含實際數字
    series_names: list[str] | None = None
```

注意此結構**完全沒有數值欄位**，這是刻意設計，逼迫 LLM 只能做「選擇」而不能做「計算」或「編造」。

## 5. 三份資料副本與一致性要求

系統中同一組數字實際上會存在**三份副本**，設計上必須保證三者一致：

| 副本 | 位置 | 用途 | 產生方式 |
|------|------|------|----------|
| ① Chart XML 快取值 | `.pptx` 內 `chart#.xml` | PPT 畫面顯示 | `add_chart()` 自動產生 |
| ② 內嵌 workbook | `.pptx` 內 `embeddings/*.xlsx` | 右鍵「編輯資料」開啟 | `add_chart()` 自動產生，與①同源 |
| ③ FR-3 外部稽核 `.xlsx` | 獨立檔案，跟 PPT 一起寄送 | 使用者/主管獨立核對、稽核 | 由 Stage 2「分析後 Excel」延伸產生，餵入**相同**的 ChartSpec |

①②由同一次 `add_chart()` 呼叫產生，保證一致；③是另一條獨立輸出路徑，但因為輸入資料源頭相同（都來自 Stage 2 分析後 Excel → MetricStore → ChartSpec），數值仍然一致。三者不會互相「連動」——即使使用者事後在 PPT 裡雙擊改了內嵌工作表的值，也不會回寫影響外部稽核 `.xlsx`，這是預期行為（生成後的手動修改屬於使用者個人用途）。

## 7. 圖表類型對應與已知限制

| 附件二要求的圖表 | python-pptx 對應方案 | 狀態 |
|---|---|---|
| 排名圖、成長率圖（長條/橫條） | `CategoryChartData` + `COLUMN_CLUSTERED` / `BAR_CLUSTERED` | 已實作並驗證 |
| 市占率圖（圓餅圖） | `CategoryChartData` + `PIE` | 已實作（`add_pie_chart()`），限制單一系列 |
| 散點圖（規模 vs 成長） | `XyChartData` | 已實作 `add_scatter_chart()`，**資料點標籤（銀行名稱）尚未支援** |
| 熱力圖 | 無原生圖表類型 | 改用原生表格 + 儲存格底色模擬，**不屬於「圖表」，右鍵無「編輯資料」選項**；不走 `add_chart()`，需另外設計 `table_builder.py` 並在 Agent 端個別處理 |
| 雙軸圖（如流通卡數＋簽帳金額疊圖） | 無高階 API | 需手動操作底層 `chart._chartSpace` lxml，插入第二個 plot 並綁定第二軸 |

### 7.1 待解決事項

- **散點圖標籤**：附件三 P.10 每個資料點旁需顯示銀行名稱（中信、玉山...），python-pptx 無高階 API，需直接操作 `c:dLbls` XML 節點。
- **雙軸圖**：附件三 P.5 為流通卡數（長條）+ 簽帳金額（折線）雙軸疊圖，需要 low-level XML 插入，且需驗證手動插入不會破壞內嵌工作表的自動同步機制。
- **熱力圖是否符合「圖表可獨立修改」要求**：目前規劃走表格模擬，需與命題要求的「圖表」定義做確認。
- **ChartAgent 的 LLM 呼叫尚未接真實 API**：`verify_llm_chart_flow.py` 尚未實作；實作時先用假回應打通契約，正式串接再替換為 `src/llm/` 的 `complete_json(prompt, schema=CHART_PLAN_SCHEMA)`，下游 validate/resolve/render 邏輯不需改動。
- **章節規劃 Agent 的中斷機制**：「NEEDS_CONFIRMATION」狀態需要對應到 API 層的非同步 job 狀態機（如 `AWAITING_USER_INPUT`），目前僅有設計，尚未實作 API 框架。

## 8. 與模板（`source/template.pptx`）的整合方式

### 8.1 模板現況

- 5 頁骨架，6 種版面配置（標題頁 / 章節標題頁 / 標題及內容頁等）
- 目前**沒有任何圖表物件**，僅有標題、內容文字框（BODY placeholder）、頁碼 placeholder

### 8.2 生成邏輯

因為模板只是骨架，生成流程是「新增內容」而非「修改既有圖表」：

```
1. 章節規劃 Agent 決定本頁對應哪個 SectionPlan（如「市場整體概況」）
2. Renderer 選擇對應版面（如「1_標題及內容」），填入章節標題
3. 圖表 Agent 已產出的 ChartSpec，依 chart_type 呼叫 CHART_SKILLS[chart_type](...)
   插入圖表到指定座標（left/top/width/height）
4. 文字生成 Agent 產出的 PageNarrative，經佔位符代入實際數值後填入內容文字框
5. 若該頁需要表格（如熱力圖模擬），另外用 python-pptx 原生 table API 插入
```

POC 中已示範套用第 4 頁（`1_標題及內容` 版面）插入圖表並成功驗證；文字生成/審查 Agent 的實際頁面組裝流程尚未實作。
