# 系統架構與資料流程

> 對象：要接手或審查這個系統的工程師。
> 目的是回答三個問題：**元件怎麼分層**、**一份 Excel 怎麼變成一份簡報**、
> **哪些邊界是不能繞過的**。
>
> 相關文件：圖表原生性的底層機制見 [`圖表原生性與資料同步設計.md`](圖表原生性與資料同步設計.md)；
> 指標引擎與模型抽換層見 [`資料引擎與LLM層設計.md`](資料引擎與LLM層設計.md)；
> 安裝與執行見 [`../README.md`](../README.md)。

## 1. 一句話架構

**確定性核心 + 受約束的模型週邊。**

系統裡所有數字都由 pandas 程式算出並存進 `MetricStore`；模型只能做三件事——
規劃章節、選圖表、寫敘事——而且輸出一律是 schema 驗證過的 JSON，**不含任何數值**。
敘事裡要提到數字只能寫佔位符，由 renderer 從 `MetricStore` 查表代入。

這個設計直接對應命題揭露的病灶：簡報上的數字與 Excel 不符。只要模型沒有寫出數字的
管道，這類錯誤在架構上就不成立。

## 2. 分層與依賴方向

```text
┌──────────────────────────────────────────────────────────────┐
│  frontend (React + Vite)          nginx 代理 /api /auth /ingestion │
└──────────────────────────────────────────────────────────────┘
                              │ HTTP
┌──────────────────────────────────────────────────────────────┐
│  backend (FastAPI)                                           │
│    api/          jobs、downloads、health                      │
│    auth/         JWT                                          │
│    ingestion/    Excel/PDF/影像 → NormalizedIngestion         │
│    worker/       generation_job_runner（非同步執行）           │
│    repositories/ S3JobRepository（job 狀態落 S3）              │
│    storage/      S3ObjectStorage（唯一 S3 出入口）             │
└──────────────────────────────────────────────────────────────┘
                              │ GenerationRequest (JSON)
┌──────────────────────────────────────────────────────────────┐
│  core                                                        │
│    contracts/generation.py       versioned JSON 契約           │
│    generation_orchestrator.py    唯一可呼叫邊界 generate_deck() │
└──────────────────────────────────────────────────────────────┘
                              │ ingestion JSON + options
┌──────────────────────────────────────────────────────────────┐
│  ppt_generation                                              │
│    data/         dataset_loader、metric_engine、MetricStore    │
│    agents/       section / chart / narrative / reviewer        │
│    charts/       chart_builder、table_builder、chart_planner   │
│    output/       renderer（PPTX）、excel_exporter（稽核 XLSX）  │
│    verification/ T1 三方數值一致性                             │
│    core/         llm_client、config、placeholders、theme       │
│    run_pipeline.py   唯一 CLI 入口                             │
└──────────────────────────────────────────────────────────────┘
```

依賴方向**單向固定**：

```text
backend → core → ppt_generation
```

四條禁止規則，由 `scripts/verify_all.py` 的靜態掃描守住（第 3 關）：

| 規則 | 理由 |
|---|---|
| `src/` 任何檔案不得 `import tools` | 量測程式不能變成產品的依賴 |
| backend 不得 import `ppt_generation` | 生成細節只能經 `core` 的契約進出 |
| core 不得 import `app` / `backend` | orchestrator 要能離開 HTTP 情境獨立測試 |
| ppt_generation 不得 import `app` / `backend` / `core` | 生成模組必須能單獨用 CLI 跑 |

最後一條的實際效益：`run_pipeline` 可以只吃一份 ingestion JSON 就跑完，
不需要起 FastAPI、不需要 S3、不需要 AWS 憑證。CI 因此能完全離線驗收。

> **只有一條 generation 路徑。** CLI、API、worker、模型比較工具全部呼叫
> `ppt_generation.run_pipeline`。不存在第二套 pipeline、engine 或 MetricStore。

## 3. 端到端資料流程

### 3.1 全景

```text
① 使用者上傳
   Excel/PDF/圖片 + prompt（+ 選填 template.pptx）
        │  POST /api/v1/jobs/generate  → 202 + job_id
        ▼
② 落 S3 並建立 job
   uploads/{job_id}/NN_{filename}
   jobs/{job_id}.json（狀態機的真相來源）
        │  asyncio.create_task
        ▼
③ backend ingestion
   識別檔型 → 偵測表頭 → 正規化 → NormalizedIngestionContract
   uploads/{job_id}/ingestion.json
        │  低信心 dataset → status=waiting_review（見 §5）
        ▼
④ core.generate_deck(GenerationRequest)
        ▼
⑤ 確定性指標計算              [無模型]
   dataset_loader → metric_engine → MetricStore
   同時產出「可計算指標白名單」與「被防呆擋下的指標及原因」
        ▼
⑥ 章節規劃 / 圖表決策 / 敘事撰寫 / 審查   [模型]
   每一步的輸出都是 schema 驗證過的 JSON，且不含數值
        ▼
⑦ 產出                        [無模型]
   renderer  → .pptx（原生圖表，內嵌 workbook）
   exporter  → .xlsx（FR-3 稽核）
        ▼
⑧ T1 三方數值比對             [無模型]
        ▼
⑨ 回存 S3
   outputs/{job_id}/…、deckspecs/{job_id}/deckspec.json
   job 狀態轉 succeeded，artifacts 附短效期簽章網址
```

### 3.2 七個階段與模型依賴

`run_pipeline --list-stages` 的實際輸出：

| # | 階段 | 需要模型 | 產物 |
|---|---|:---:|---|
| 1 | `metrics` Stage 1-3 資料讀取與指標計算 | — | `MetricStore`、可計算指標白名單 |
| 2 | `sections` Stage 4-1 章節規劃 | ✔ | `SectionPlan[]`（含每頁 metric 白名單） |
| 3 | `charts` Stage 4-2 圖表決策 | ✔ | `ChartPlan[]` → 查表後成 `ResolvedChart` |
| 4 | `narratives` Stage 4-3 敘事撰寫 | ✔ | `PageNarrative[]`（只有佔位符） |
| 5 | `review` Stage 4-4 審查 | ✔ | `ReviewResult[]` |
| 6 | `render` Stage 5-6 產出檔案 | — | `.pptx` + 稽核 `.xlsx` |
| 7 | `verify` Stage 7 三方數值比對 | — | T1 報告 |

`--stage <name>` 可以跑到任一階段就停；每階段結果寫成
`<output-dir>/stages/NN_<stage>.json`，這是排查「哪一步開始不對」的主要工具。

**四個階段完全不需要模型**（1、6、7 加上 ingestion）。因此 `--fake-llm`
能在零模型呼叫的情況下驗證超過一半的管線，這是 CI 可以 deterministic 的原因。

## 4. 模組間的 JSON 契約

跨模組**只傳 schema 驗證過的 JSON**，不互相抓內部狀態。

| 邊界 | 契約 | 定義位置 |
|---|---|---|
| API → worker | S3 物件參照 + 持久化 job model | `app/schemas/jobs.py` |
| ingestion → core | `NormalizedIngestionContract`（`contract_version="1.0"`） | `core/contracts/generation.py` |
| worker → core | `GenerationRequest`（`contract_version="1.1"`） | 同上 |
| core → worker | `GenerationResult` + `GeneratedArtifact[]` | 同上 |
| engine → agents | 序列化 `MetricStore` / catalog | `ppt_generation/contracts/stages.py` |
| agents → renderer | section / chart / narrative / review schemas | 同上 |
| renderer → validator | PPTX + 稽核 XLSX + resolved chart specs | — |

### 為什麼契約要帶版號

`GenerationRequest.contract_version` 是 `Literal["1.1"]`——**不符就直接驗證失敗**，
不會半懂半不懂地跑下去。`NormalizedIngestionContract` 同理（`"1.0"`）。

這條規則有實際代價：目前 `run_pipeline --sample` 就是因為內建範例 payload 缺
`contract_version` 而在 Stage 1-3 中斷（`data/dataset_loader.py:236`）。
契約收緊時，所有進入點都要一起更新——這是已知缺口。

### 幾個關鍵欄位

`GenerationOptions` 有一條 `model_validator`：
`render_reserve_seconds + output_reserve_seconds` 必須小於 `deadline_seconds`。
時間預算在 job 建立時就驗證，不會等到跑到一半才發現保留時間比總時間還長。

`GenerationRequest` 的註解寫明：`ingestion_path` 與 `output_dir` 是
**worker 本機的暫時落地**，持久化的來源仍在 `source_objects` 與 backend job。
**原始 Excel 永遠不會從 core 穿進 ppt_generation**——後者只看得到正規化後的 JSON。

## 5. Job 狀態機與人工複核

`JobStatus`：

```text
queued ──► running ──► succeeded
   │          │
   │          ├──► waiting_review ──(全部 dataset 通過)──► queued
   │          │
   └──────────┴──► failed
```

`JobStage`（回報進度用）：`queued` → `parsing_intent` → `analyzing_data` →
`reviewing_data` → `writing_insights` → `rendering` → `validating` → `completed` / `failed`。

ingestion 對信心不足的 dataset 標記 `requires_human_review`，job 轉入
`waiting_review` 並停住。使用者透過三個端點處理：

```text
GET  /api/v1/jobs/{id}/review                       取得待複核 dataset + 來源預覽
POST /api/v1/jobs/{id}/datasets/{dataset_id}/review 核可 / 退回 / 修正
POST /api/v1/jobs/{id}/resume                       全部通過後續跑
```

`resume_job()` 會**重新驗證**：仍有 `requires_human_review` 或
`review_status ∈ {pending, rejected}` 的 dataset 就拒絕續跑。
複核結果寫回同一份 `uploads/{job_id}/ingestion.json`，因此 Refresh 時
人工修正不會遺失。

> **限制**：job 目前以 process-local `asyncio.create_task` 執行。程序在
> queued/running 中重啟時，沒有重新 claim 與 retry 機制。job 狀態本身已落 S3，
> 所以資料不會丟，但那個 job 不會自己繼續跑。

## 6. S3 物件佈局

S3 是**所有輸入、輸出與 job 狀態的唯一持久化位置**。worker 的本機目錄是
`tempfile.TemporaryDirectory()`，函式結束即刪除。

```text
s3://{S3_BUCKET}/
├── jobs/{job_id}.json                          job 狀態（狀態機真相來源）
├── uploads/{job_id}/
│   ├── NN_{filename}                           原始上傳（依上傳順序編號）
│   ├── template/{filename}                     選填的自訂 PPTX 模板
│   └── ingestion.json                          正規化結果（人工複核寫回同一份）
├── outputs/{job_id}/
│   ├── {來源檔名}-分析簡報.pptx
│   ├── {來源檔名}-分析資料.xlsx
│   ├── verification.json                       T1 報告
│   ├── generation_manifest.json                產出清單、sha256、模型路由
│   └── stages/NN_*.json                         階段中間結果
└── deckspecs/{job_id}/deckspec.json            Refresh 用 spec（另存一份）
```

### 產出怎麼給使用者看

bucket 不公開。流程是**私有 bucket + 短效期預簽網址**：

```text
GET /api/v1/jobs/{job_id}
   → job_service.get_job() 逐一檢查 artifact
   → is_authorized_artifact_key(job_id, filename, object_key)
        key 必須以 outputs/{job_id}/ 開頭、不含 ".."、檔名相符
   → storage.presigned_download_url(key)   ExpiresIn=S3_PRESIGN_EXPIRES_SECONDS
   → 回傳 download_url，前端 <a href download>
```

`get_job()` **每次呼叫都重新簽章**，不信任持久化的舊 URL。網址過期只要再查一次
job 就會拿到新的。另有 `GET /api/v1/downloads/{job_id}/{filename}` 做同樣的授權
檢查後 307 轉址，供單檔重新取得連結。

> **安全性現況**：授權只做到「這個 key 屬於這個 job」。生成、ingestion、下載端點
> 都沒有認證，任何知道 `job_id`（UUID4）的人都能取得該 job 的產出。目前只有
> `POST /jobs/{id}/send` 要求 JWT。對外部署前必須補認證。

## 7. 數值正確性的三道防線

### 第一道：模型沒有寫數字的管道

模型的輸出 schema 裡**沒有可以放數值的欄位**。`ChartPlan` 只有
`metric_key` / `series_names` / `chart_title`；`PageNarrative` 只有含
`{{metric_key|series_name|selector}}` 佔位符的文字。

`chart_planner.resolve_chart_plan()` 是**全系統唯一把數字填進圖表的地方**，
數值全部來自 `MetricStore` 查表。

### 第二道：防呆白名單

`metric_engine` 除了算指標，還輸出兩份清單：可計算指標、被擋下的指標及原因。
資料範圍不足的指標不會產出——例如只有單年資料就不能算 YoY。

`section_planner._sanitize_sections()` 會剔除模型幻想出來的 `metric_key`，
即使模型回傳了不存在或被擋下的指標，也不會流入下游。多系列指標必須明確限縮
`series_names`，留空**不解讀為「全部」**。

### 第三道：T1 三方數值比對

同一組數字有三份副本：

| # | 副本 | 產生時機 |
|---|---|---|
| ① | Chart XML 快取值（畫面顯示） | `add_chart()` |
| ② | 內嵌 workbook（右鍵編輯資料） | 同一次 `add_chart()` |
| ③ | FR-3 外部稽核 `.xlsx` | 獨立輸出路徑，同一份 `ChartSpec` |

①② 由同一次 `add_chart()` 呼叫保證一致——這是「所有圖表必須經單一入口生成」
這條規則的全部理由。③ 因輸入源頭相同（同一個 `MetricStore`）而一致。

原生表格沒有內嵌 workbook，改以「儲存格文字 ↔ 稽核 Excel」反向解析比對，
因此 `table_builder.format_value()` 必須是表格文字的唯一產生入口。

## 8. 審查與失敗退讓

審查分兩層：

**規則層（確定性，不呼叫模型）**
- 引用的 `metric_key` 是否都在白名單內
- 敘事是否含裸數字
- 方向詞（成長／衰退／領先）是否與實際數值正負號矛盾
- 價格類指標是否出現買賣建議或報酬保證

> **待合併**：分支 `ppt_current` 另外加了一組「代入後」的文字品質檢查
> （錯別字、疊字、簡體字、單位重複），尚未併入 `main`。它必須跑在**佔位符
> 代入之後**，因為 `format_value()` 產出的值自帶單位（`名` → `第 3 名`、
> `%` → `12.3%`），模型只看得到佔位符，於是「排名第 {{…}} 名」這種
> **模板完全合法**的寫法代入後會變成「排名第第 3 名名」——檢查原始模板抓不到。

**語意層（模型）**
- 圖表類型是否適合資料形狀
- 因果推論是否過度延伸、是否與資料注意事項衝突
- 用詞是否得體、語句是否通順

### `required` 模式的退讓階梯

```text
① 審查發現問題
      │ 把問題清單原文回饋給 narrative_writer
      ▼
② 重寫該頁（時間預算內持續重試）
      │ 同一問題重複出現，或重試次數超過 LLM_REPAIR_ESCALATE_AFTER
      ▼
③ 升級到 LLM_MODEL_WRITER_FALLBACK 再試
      │ 仍失敗
      ▼
④ 套用確定性敘事模板（build_deterministic_fallback）
      │ 連模板都過不了硬性規則
      ▼
⑤ RuntimeError（代表系統本身有 bug，該中斷）
```

所以**頁面不會因為錯字被丟掉**，最壞情況是退到中性、完全可追溯的確定性敘事。
過程中 `seen_candidates` 擋掉模型回傳重複候選，`last_valid` 記住「規則層全過、
語意層沒過」的最佳候選，最後採用它並在 `warning` 註明。

`strict` 模式不同：`MAX_REVIEW_REPAIR_ATTEMPTS = 2` 次修不好就 fail-fast，
不退到模板。

> 第 ④ 層是最後的安全網，因此**確定性模板本身必須永遠通過整個規則層**。
> `hard_issues_for()` 跑的是完整規則層，新增任何規則時都要驗證模板不會被它擋下，
> 否則就是在安全網上開洞。

## 9. 時間預算

SLA 從 `POST /generate` 落庫回 `202` 開始算：

```text
GENERATION_DEADLINE_SECONDS = 1500（25 分鐘）
├── 模型階段可用時間（其餘）
├── GENERATION_RENDER_RESERVE_SECONDS = 240   保留給 render / XLSX / T1
└── GENERATION_OUTPUT_RESERVE_SECONDS = 150   保留給 S3 上傳與緩衝
```

時間預算一路傳到 `llm_client`：每次請求前重算剩餘時間，`_cap_request_timeout()`
把單次 SDK timeout 壓到不超過剩餘額度，重試退避若會超過期限就直接拋
`LLMDeadlineExceeded`。**寧可少一次重試，也不能吃掉 render 的保留時間**——
產不出檔案比敘事不完美嚴重得多。

平行度由 `LLM_MAX_PARALLEL`（預設 16，下限 4）與 `LLM_RPM_LIMIT`（預設 24）控制，
後者是 per provider/region/model 的請求啟動預算，用來避免撞供應商限流。

## 10. 模型抽換層

`ppt_generation/core/llm_client.py` 對外只有兩個進入點：

```python
complete_json(prompt, schema, ...)          # 要求符合 schema 的 JSON
complete_tool_call(prompt, tool_schemas, ...)  # 從白名單挑一個工具並填參數
```

呼叫端（各 agent）**不知道自己在跟哪家模型說話**。切換後端只改環境變數。

兩條後端路徑：

| provider | 路徑 | 憑證 |
|---|---|---|
| `bedrock` | AWS Bedrock Converse API | SDK 簽章（IAM／Instance Profile），**必須顯式 `AWS_REGION`** |
| `openai` / `google` / `vllm` / `ollama` / `litellm` | OpenAI 相容 `chat.completions` | API key（地端通常不驗證） |

### 能力差異的降級路徑

並非所有模型都支援 OpenAI 那套完整功能，因此有三個模式開關，依模型名稱自動選預設值：

| 開關 | `native` | 降級 |
|---|---|---|
| `LLM_TOOL_MODE` | OpenAI `tool_calls` | `json`：以 JSON 輸出模擬工具選擇 |
| `LLM_JSON_MODE` | `response_format=json_object` | `prompt`：僅靠提示詞要求 JSON |
| `LLM_SYSTEM_MODE` | system role | `merge`：併入首個 user 訊息 |

Gemma 系列三項都自動降級。模擬工具呼叫的**安全性與原生路徑等價**：工具名稱仍
只能來自白名單，參數仍經 schema 驗證，模型無法藉此執行未註冊的程式碼路徑。

另有兩個實戰得來的處理：schema 一律附在 prompt 裡（`response_format` 只保證
「是一個 JSON」，不保證欄位名稱——實測模型會把 `sections` 猜成 `pages`）；
非必填欄位給 `null` 視為沒給（模型很常明確寫出 `"question_to_user": null`）。

## 11. 沒有向量索引

本系統**沒有 RAG，也沒有向量檢索**。對應的角色是兩個確定性產物：

| 產物 | 角色 |
|---|---|
| `config/metric_definitions.json` | 指標定義：可以算什麼、公式、單位 |
| `MetricStore`（執行期建立） | 該次生成的唯一數值真相來源 |

模型看到的是 `store.catalog_as_prompt()`——**只有 metadata，沒有任何數值**。
它能引用的 key 限於 `computable_metric_keys()`。這是「模型不參與計算」在
資料流上的具體落地：模型連數值都看不到，自然無從寫出。

唯一例外是**審查階段**：`reviewer.build_prompt()` 會把已代入數值的文字交給模型，
因為判斷「10.7% 高於 11.0%」這類邏輯錯誤必須看到實際數字。這不違反原則——
模型在此只讀不寫，其輸出（APPROVED／REJECTED）不含任何數值。
